Principal contract: a real host verifier validates its own session on **every** request and passes `{authenticated:true, issuer, subject, expiresAt, csrfToken}`. The public adapter hashes issuer/subject and maps them to an opaque stable commerce principal. Logout/revocation rejects access; a new verified session for the same issuer/subject restores ownership; another account never inherits the local appearance cache. No client `userId`, dev identity header, email, localStorage account ID or exported save authorizes a purchase. Host quest context must be read from the host's authority; fixture quest mutation routes stay disabled in principal mode.

Proposed targeted verification before any private change is shipped: existing first-outfit rules/presentation tests plus new adapter tests for same-account re-login, account switching, expired/revoked sessions, held rights and offline fallback; gate tests asserting all three conditions; save tests proving before/after gold, seal, rumor and story values unchanged. Existing progress remains usable with commerce disabled or unavailable. Exact host-auth ownership and server quest authority require a separate reviewed design before private implementation.

## Existing account integration candidate

The read-only audit also identifies `kaito_web/server/coop-accounts.mjs` and its existing `createCoopAccounts().identify` / `authenticate` boundary, consumed by `kaito_web/server/village-chat-service.mjs` and `kaito_web/src/platform/villageChatGateway.ts`. The account's stable internal ID is the candidate **subject**, with a fixed environment-specific issuer. Use the host's existing in-memory account service and only its verified-token lookup path; do not copy its implementation or credentials table into this public project.

Critical distinction: `identify` with **no token creates a new guest**. The proposed commerce verifier must reject a missing token before calling it, never use that guest-creation branch, never trust the requested display name, and never forward the opaque token to analytics or AI. Existing registered-account login rotates the token while retaining account identity. Validate the current token for every commerce request so replacement/revocation takes effect. Issue a separate short-lived server-bound commerce session/CSRF credential; its expiry cannot be inferred from the legacy opaque-token format, which has no embedded expiry.

The host also permits browser-only guest identities that cannot recover after token loss. Before enabling paid purchases, the private integration must distinguish recoverable registered/linked accounts from such guests; this account-policy check and its UI are not implemented. Do not claim cross-device recovery for guests. Proposed deployment mounts the bridge at a reviewed same-origin route with host-owned authentication; it does not expose the local Codex gateway or add database/admin permissions. No changes to the existing chat service or its provider configuration are made in this iteration.
